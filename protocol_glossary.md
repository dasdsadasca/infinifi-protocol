# InfiniFi Protocol Glossary

This glossary provides definitions for key terms, concepts, contract names, and token names used within the InfiniFi protocol, based on the provided analysis documents.

| Term                       | Definition                                                                                                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core Contracts & Concepts** |                                                                                                                                                                                                                                       |
| `InfiniFiCore.sol`         | The central access control and role management contract for the protocol. It defines roles (e.g., `GOVERNOR`, `PAUSE`) and their administrative hierarchies using OpenZeppelin's `AccessControlEnumerable`.                           |
| `CoreControlled.sol`       | An abstract contract inherited by other protocol contracts to provide standardized interaction with `InfiniFiCore` for role-based access control, pausable functionality, and emergency actions.                                         |
| `InfiniFiGatewayV1.sol`    | The main user-facing entry point for the InfiniFi protocol. It orchestrates operations like minting, redeeming, locking, unwinding, and voting by interacting with various specialized controller and token contracts.                     |
| Role-Based Access Control (RBAC) | A security model where access to functions and administrative privileges is determined by roles assigned to addresses, managed by `InfiniFiCore`.                                                                                      |
| `CoreRoles.sol` (Library)  | A library likely defining constants for various role identifiers (e.g., `GOVERNOR`, `ENTRY_POINT`, `FARM_MANAGER`, `RECEIPT_TOKEN_MINTER`) used throughout the protocol for access control checks.                                        |
| Epoch                      | A discrete period (e.g., a week) used by the protocol for time-sensitive operations like voting in `AllocationVoting` and managing unwinding periods in `LockingController` and `UnwindingModule`. Defined by `EpochLib`.               |
| `EpochLib.sol` (Library)   | A library providing utility functions for epoch calculations, such as converting timestamps to epoch numbers and vice-versa.                                                                                                          |
| Pausable Functionality     | A feature, provided by `CoreControlled` (inheriting OpenZeppelin's `Pausable`), allowing authorized roles (`PAUSE_ROLE`, `UNPAUSE_ROLE`) to halt and resume certain contract operations.                                                |
| Emergency Action           | A function in `CoreControlled` (callable by `GOVERNOR`) allowing arbitrary low-level calls to other contracts, intended for critical interventions.                                                                                    |
| Zap                        | A feature (e.g., `zapIn` in `InfiniFiGatewayV1`) allowing users to perform multiple operations (e.g., swap an input token to USDC, then mint and stake iUSD) in a single transaction.                                                     |
| **Funding Module**         |                                                                                                                                                                                                                                       |
| `MintController.sol`       | Manages the minting of new `ReceiptToken`s in exchange for an underlying asset (e.g., USDC). It calculates the token exchange rate using `Accounting` and interacts with `ReceiptToken` to mint.                                   |
| `RedeemController.sol`     | Manages the redemption of `ReceiptToken`s for the underlying asset. It handles both immediate redemptions (if liquid) and queued redemptions (via `RedemptionPool` logic) if liquidity is insufficient.                               |
| `RedemptionPool.sol`       | An abstract contract providing the core logic for managing a redemption queue. It handles enqueueing, funding, and claiming redemption requests. Token transfers are handled by the inheriting contract (`RedeemController`).             |
| `ReceiptToken.sol`         | The contract for the primary yield-bearing token of the protocol (e.g., iUSD), representing a user's deposit. It's an ERC20 token with minting/burning controlled by `MintController` and `RedeemController`.                         |
| iToken / Receipt Token     | A generic term for the protocol's main yield-bearing token (e.g., iUSD) issued by `ReceiptToken.sol`.                                                                                                                                  |
| iUSD                       | An example name for a `ReceiptToken` pegged to USD, representing a user's deposit of a USD-stablecoin like USDC.                                                                                                                      |
| Redemption Queue           | A system managed by `RedeemController` (using `RedemptionPool` logic) to handle redemption requests when there isn't enough immediate liquidity. Users' requests are queued and processed as assets become available.                   |
| Asset Token                | The underlying collateral asset (e.g., USDC, WETH) that users deposit to mint Receipt Tokens, or receive when redeeming Receipt Tokens.                                                                                                 |
| **Locking Module**         |                                                                                                                                                                                                                                       |
| `LockingController.sol`    | Orchestrates the token locking mechanism. Users lock `ReceiptToken`s for defined periods ("buckets") to receive `LockedPositionToken`s and potentially enhanced yield. Manages reward/loss distribution for locked and unwinding tokens. |
| `UnwindingModule.sol`      | Manages locked positions that are in the "unwinding" phase. Handles the gradual release of tokens over the unwinding period and distributes rewards/losses to these positions.                                                          |
| `LockedPositionToken.sol`  | An ERC20 token representing a user's locked position for a specific unwinding duration (bucket). Different lock durations have distinct `LockedPositionToken` contracts. Also referred to as "share tokens".                            |
| liUSD                      | An example name for a `LockedPositionToken`, representing iUSD locked for a specific duration.                                                                                                                                        |
| Bucket (Locking)           | A predefined lock-up duration (e.g., 2, 4, 6 weeks/epochs) in the `LockingController`, associated with a specific `LockedPositionToken` and reward multiplier.                                                                      |
| Unwinding                  | The process of transitioning a locked position back to liquid `ReceiptToken`s. It occurs over a set number of epochs, during which rewards/losses may still apply. Managed by `UnwindingModule`.                                      |
| `UnwindingPosition` (Struct) | A struct in `UnwindingModule` storing details of a user's unwinding position, including shares, start/end epochs, and reward weight parameters.                                                                                      |
| Share Token                | Another term for `LockedPositionToken`, representing a share of the `ReceiptToken`s locked in a specific bucket within the `LockingController`.                                                                                          |
| Reward Weight              | A value representing a user's claim on rewards, typically influenced by the amount locked and the duration of the lock (via multipliers). Used in `LockingController` and `AllocationVoting`.                                          |
| **Governance Module**      |                                                                                                                                                                                                                                       |
| `AllocationVoting.sol`     | Enables users with locked positions (`LockedPositionToken`s) to vote on how protocol assets should be allocated across different yield-generating farms. Votes are weighted by the user's `rewardWeight` from `LockingController`.      |
| `AllocationVote` (Struct)  | A struct used in `AllocationVoting` to define a user's vote for a specific farm, containing the farm's address and the percentage weight of the user's voting power allocated to it.                                                  |
| Farm Allocation            | The distribution of protocol-controlled assets among various yield-generating farms, influenced by user votes through `AllocationVoting`.                                                                                               |
| `FarmWeightData` (Struct)  | A struct in `AllocationVoting` that stores the voting weight for a farm, distinguishing between `currentWeight` (for the active epoch) and `nextWeight` (accumulating for the next epoch).                                            |
| **Finance & Integrations** |                                                                                                                                                                                                                                       |
| `YieldSharing.sol`         | Central contract for protocol value accrual. It calculates overall profit/loss (`unaccruedYield`) by comparing total farm asset values (from `Accounting`) with `ReceiptToken` supply, then distributes profits or applies losses.     |
| `Accounting.sol`           | Responsible for asset valuation. It aggregates asset values from all registered farms (via `FarmRegistry`) and uses price oracles to determine their total value (typically in USD).                                                   |
| `FarmRegistry.sol`         | A directory for all integrated yield-generating farm contracts. It categorizes farms by asset type and allows other protocol components to discover and query them.                                                                  |
| `Farm.sol` (Base)          | An abstract base contract defining the common interface (e.g., `assets()`, `deposit()`, `withdraw()`) and core functionalities (e.g., cap, slippage control) for all specific farm implementations.                                   |
| `AaveV3Farm.sol`           | A specific farm implementation for depositing assets into the Aave V3 lending protocol to earn yield.                                                                                                                                 |
| `PendleV2Farm.sol`         | A specific farm implementation for interacting with Pendle V2, allowing investment in Principal Tokens (PTs) to earn fixed yield or participate in other Pendle strategies. Involves managing maturities and yield interpolation.      |
| Farm                       | A generic term for a contract that integrates with an external DeFi protocol or strategy to generate yield on deposited assets. Examples: `AaveV3Farm`, `PendleV2Farm`.                                                               |
| Oracle (Price Oracle)      | An external contract or system that provides price feeds for assets (e.g., USDC/USD, ETH/USD). `Accounting` uses these oracles to value assets held in farms. `FixedPriceOracle` is a specific type mentioned.                     |
| `FixedPriceOracle.sol`     | A specific type of oracle contract mentioned in `YieldSharing` that allows its price to be set directly, used for the `ReceiptToken` itself in extreme loss scenarios.                                                                 |
| Unaccrued Yield            | The net profit or loss of the protocol, calculated by `YieldSharing` as the difference between the total value of assets in farms (per `Accounting`) and the total supply of `ReceiptToken`s.                                         |
| Safety Buffer              | An amount of `ReceiptToken`s held by `YieldSharing` to absorb small initial losses before they are propagated to users or other modules.                                                                                                |
| Performance Fee            | An optional fee on profits, configured in `YieldSharing`, which can be directed to a specified recipient.                                                                                                                             |
| `StakedToken.sol`          | A contract (e.g., for siUSD) where users can stake their `ReceiptToken`s to earn a share of protocol yield, as distributed by `YieldSharing`.                                                                                          |
| siUSD                      | An example name for a `StakedToken`, representing iUSD staked in the `StakedToken` contract.                                                                                                                                            |
| Asset (Farm Asset)         | The specific underlying crypto asset (e.g., USDC, WETH) that a particular farm accepts for deposit and yield generation.                                                                                                                |
| Liquidity (Farm)           | The amount of `assetToken` that a farm contract can immediately make available for withdrawal. For some farms (like `PendleV2Farm`), this might be different from total `assets()` due to wrapped positions.                            |
| Maturity (Pendle Farm)     | A specific timestamp associated with a Pendle market (and thus a `PendleV2Farm`) at which its Principal Tokens (PTs) can be redeemed for their underlying assets.                                                                      |
| Yield Interpolation (Pendle Farm) | The process in `PendleV2Farm` of estimating the accrued yield on Principal Tokens (PTs) before their maturity date, to provide a more accurate current valuation of the farm's assets.                                          |
| **Key Admin Roles**        |                                                                                                                                                                                                                                       |
| `GOVERNOR` (Role)          | The highest administrative role with powers to manage other roles, set critical parameters, enable assets/farms, and perform emergency actions. Typically assigned to the deployer initially.                                        |
| `PROTOCOL_PARAMETERS` (Role) | A role with permissions to set non-critical operational parameters, such as farm caps, slippage tolerances, `AllocationVoting` settings, and certain `YieldSharing` parameters.                                                      |
| `ENTRY_POINT` (Role)       | A role, typically assigned to `InfiniFiGatewayV1`, authorizing it to call restricted functions on backend controllers (e.g., `MintController.mint`, `RedeemController.redeem`, `LockingController.createPosition`).                  |
| `RECEIPT_TOKEN_MINTER` (Role) | A role, typically assigned to `MintController`, authorizing it to mint new `ReceiptToken`s.                                                                                                                                       |
| `RECEIPT_TOKEN_BURNER` (Role) | A role, typically assigned to `RedeemController`, authorizing it to burn `ReceiptToken`s.                                                                                                                                         |
| `LOCKED_TOKEN_MANAGER` (Role) | A role, typically assigned to `LockingController` (and `UnwindingModule` for specific actions), authorizing it to mint/burn `LockedPositionToken`s and manage the unwinding process.                                                  |
| `FARM_MANAGER` (Role)      | A role authorized to manage farm operations like calling `deposit()` or `withdraw()` on `Farm` contracts to move funds between the farm contract and the external DeFi protocol.                                                      |
| `ORACLE_MANAGER` (Role)    | A role authorized to set and update price oracle addresses in the `Accounting` contract.                                                                                                                                              |
| `FINANCE_MANAGER` (Role)   | A role authorized to trigger reward deposits or apply losses in the `LockingController` and potentially `YieldSharing`.                                                                                                               |
| `TRANSFER_RESTRICTOR` (Role) | A role authorized to restrict transfers of `LockedPositionToken`s, used by `AllocationVoting` after a user votes.                                                                                                                    |
| `FARM_SWAP_CALLER` (Role)  | A role authorized to execute swap functions on certain farms like `PendleV2Farm` (e.g., `wrapAssetToPt`, `unwrapPtToAsset`), likely for managing complex asset transformations.                                                        |
